# capa_paymentguard

A showcase of [Capa](https://github.com/nelsonduarte/capa-language)'s
**capability discipline** and **information-flow control** applied to a
payment-transaction security core, modelled on the requirements of
PCI DSS v4.0.1, PSD2 / SCA, ISO/IEC 27001, RGPD and OWASP.

It is built to demonstrate the one property no mainstream language gives
you for free:

> **a flow the analysis detects from a card number to a log line or a
> network call, not masked, is a build error in `process` (`@strict_ifc`)
> and a warning elsewhere, and every sanctioned disclosure is recorded,
> with its reason, in the manifest.**

## What this is, and what it is NOT

This is a **language showcase**, not a production payment system. Read
the honesty section below before drawing any other conclusion.

### The strong claims (these are real)

- **Information-flow control.** Card data (`pan`, `cvv`) and credentials
  are typed `@secret`. The compiler propagates that label through every
  derived value and reports, at compile time, a `@secret` value it finds
  reaching a public sink (`Stdio.println`, `Fs.write`, `Net.post`, ...).
  See `leaky_example.capa` for the violation being caught, and
  `mask.capa` for the sanctioned masking of cardholder data; the other
  audited crossings (the authorization decision and the PAN-blocklist
  hit) live at their sinks in `main.capa`.
- **Least privilege, checked by the compiler.** The fraud / AML engine
  (`fraud.capa`) takes **no capabilities at all**: its manifest records
  an empty capability set for every function in it, provable from their
  types, with `Net`, `Fs`, `Clock` and `Env` among the excluded
  capabilities. `main` declares only `Stdio` and `Fs`, and no function in
  the program declares `Net`, `Proc`, `Db` or `Unsafe`.
- **Auditable disclosure.** Every sanctioned secret-to-public bridge is
  a `declassify(value, reason: "...")` call. The reasons are emitted
  into the Capa manifest as each function's `declassifications` list: a
  machine-readable record of where, and why, the program deliberately
  discloses cardholder data (see `conformity/manifest.json`). This is a
  PCI-relevant compliance artifact generated by the compiler, not
  written by hand.
- **Built on a hardened compiler floor (`capa >= 1.18.1`).** The IFC
  checks above rely on fixes that landed in Capa `1.3.0`, with further
  fixes in later releases, each with its own advisory. Capa `1.3.0`
  fixed two soundness gaps that
  let the `@secret` label be silently dropped: the value of a `match` /
  `if` expression or a capturing closure came out public, and a
  captured-`@secret` closure passed to a higher-order function that
  invoked it and sank the result leaked across the function boundary.
  See the compiler advisory
  [`docs/advisories/2026-06-16-soundness.md`](https://github.com/nelsonduarte/capa-language/blob/main/docs/advisories/2026-06-16-soundness.md).
  That `1.3.0` boundary is real and was re-measured here rather than
  taken on trust: delete the `declassify` in `print_decision` and compile
  `main.capa`, and `1.2.0` reports four flows while `1.3.0` and `1.19.0`
  report five. The one `1.2.0` cannot see is the `@secret` decision
  reaching `Stdio.println` through the value of a `match` expression,
  which is precisely the gap the advisory describes.
  The manifest nevertheless declares `>=1.18.1`, because `1.3.0` is a
  bound on that *check* and not on the *build*. No released binary
  before `1.18.1` can run `capa test` at all: under PyInstaller
  `sys.executable` is the capa binary and it rejects `-m`, so every
  release from `1.3.0` to `1.18.0` fails this repository's own test with
  `capa: error: unrecognized arguments: -m .../test_pan_blocklist.capa`.
  A floor a downloader can obey has to be the higher of the two. The full
  measurement is recorded in `capa.toml`.
- **The declassify bridges are load-bearing, not decorative.** This is
  the honest test of the claim above: under `@strict_ifc` (which
  `main.process` opts into), deleting a `declassify` makes the program
  stop compiling, because a `@secret` value then reaches a public sink.
  The PAN-blocklist path shows it concretely: the `@secret` PAN
  fingerprint is matched (in constant time) against a public watchlist,
  and a hit is written to a fraud-alert file through `Fs.write`. Both
  the match boolean and the matched fingerprint must be declassified
  there; remove either and `capa --check main.capa` fails with an
  information-flow error (a `@secret` value at `Fs.write`, or `Fs.write`
  running under secret control flow). The disclosures are required by
  the data flow, not asserted by a comment.
- **Tamper-evident audit log.** `audit.capa` chains each log line to the
  previous one (`audit.capa`), so editing any earlier entry breaks every
  later chain value.
- **Deterministic, explainable risk.** `fraud.capa` returns a verdict
  plus the list of reasons that produced it (regulatory requirement: risk
  decisions must be justifiable).

### The honest caveats (do not deploy this)

- **The integrity / authentication crypto is REAL; confidentiality and
  the credential KDF are still stubs.** The HMAC-SHA256 used for the
  tamper-evident audit chain, the PAN fingerprint, and the PSD2
  dynamic-linking code, and the constant-time tag comparison, all come
  from [`capa_hash`](https://github.com/nelsonduarte/capa_hash): a
  zero-capabilities Capa library whose release tag is GPG-signed and
  SLSA-attested, verified by `capa install`. Those values are genuine
  HMAC-SHA256 (cross-checked against Python's `hmac`), not placeholders.
  What stays FAKE, in `crypto_stub.capa`, is exactly what `capa_hash`
  does not (and should not) cover: the credential **KDF** (`slow_hash`,
  which a real system makes memory-hard with Argon2id, never a bare SHA)
  and the at-rest **cipher** (`encrypt`, which a real system makes
  AES-256-GCM under a KMS data key). Those two must still be replaced
  with vetted primitives behind a KMS before any deployment. The
  showcase is about the data-flow discipline *around* the crypto, which
  Capa checks; the integrity half of the crypto is now real and
  verifiable, the confidentiality / KDF half is honestly stubbed.
- **The information-flow check has known boundaries.** It tracks
  direct flows (values, parameters, interpolation, derived values,
  function results), aggregate literals, and mutable containers (a
  secret `push`ed / `add`ed / `set` into a `List` / `Set` / `Map` taints
  the container, so a later read keeps the label). What it does NOT do:
  (a) label a callee's parameter implicitly: inside a callee a parameter
  is `@secret` only when annotated, and a secret argument that reaches a
  sink through a callee is reported at the call site when the analysis
  detects the flow; and (b)
  track individual elements of a list, tuple, or map, where the
  granularity is the whole aggregate (a struct field declared `@secret`
  keeps its label per field). And it is a check, not a proof: an
  accepted program is not thereby shown free of secret-to-sink flows.
- **No real persistence, concurrency, or atomicity.** Idempotency is an
  in-memory set; the audit log is a read-modify-write file. Real
  transactional integrity, resilience, and scale are out of scope.
- **ML anomaly detection is out of scope.** Only deterministic,
  explainable rules, which is the part a regulator can audit line by
  line (and which the brief's explainability requirement favours).

## Layout

| File | Role | Capabilities |
|---|---|---|
| `domain.capa` | shared types; `@secret` on cardholder data | none |
| `crypto_stub.capa` | the two remaining **FAKE** placeholders: credential KDF + at-rest cipher | none |
| `capa_hash` (dependency) | **real** HMAC-SHA256 + constant-time compare (zero-cap, SLSA-verified) | none |
| `mask.capa` | cardholder-data masking + the at-rest `declassify` bridges; the keyed PAN fingerprint (kept `@secret`) | none |
| `validate.capa` | structural validation, PSD2 dynamic linking, idempotency | none |
| `auth.capa` | SCA / MFA (>= 2 factor classes), PSD2 exemptions, lockout | none |
| `fraud.capa` | deterministic, explainable risk / AML rules; constant-time PAN-blocklist match | **none** |
| `audit.capa` | tamper-evident, append-only logging of masked data | `Fs` |
| `main.capa` | the section-7 transaction lifecycle, wired together; the audited decision-output and PAN-blocklist `declassify` bridges | `Stdio`, `Fs` |
| `leaky_example.capa` | counter-example: the leak the compiler rejects | (does not build clean, on purpose) |

## Run it

```sh
# One-time: import the publisher key this repository ships, then vendor
# + verify the capa_hash dependency. `capa install` runs git verify-tag
# against that key and checks the SLSA provenance, then writes
# capa.lock. capa_hash holds zero capabilities, so this adds
# a verifiable dependency without widening the program's capability
# surface (least privilege still holds).
gpg --import publisher.asc
capa install

# Type-check + information-flow check (clean: no finding)
capa --check main.capa

# Check the capability ceiling capa.toml declares, max = ["Fs", "Stdio"].
# It covers the import closure of the entry it is given and nothing
# else, so the release names all eight compiling modules rather than
# relying on main.capa's closure covering them today.
capa --check-capabilities main.capa

# Run the four demo scenarios (approve / decline / tampered /
# blocklisted PAN). The last writes a line to fraud_alerts.txt.
capa --run main.capa

# See the information-flow checker reject a raw-PAN leak
capa --check leaky_example.capa

# Regenerate the full CRA conformity pack (SBOMs, manifest, VEX, provenance)
./generate.sh
```

### Running as a stock WASI component (experimental, opt-in)

The same source builds and runs as a stock **WASI Preview 2** component,
runnable on any WASI runtime without the Capa host:

```sh
capa --wasm --component --wasi --run main.capa
```

This produces the same four scenarios and the same `audit_log.txt` /
`fraud_alerts.txt` (byte-for-byte, modulo line endings; the HMAC audit
chain is identical). No `--preopen` is needed: every filesystem path in
this program is a literal routed through a helper (`"audit_log.txt"`,
`"fraud_alerts.txt"`), which the compiler resolves by constant
propagation, so the component's filesystem authority is fixed at compile
time rather than taken from an argument.

The component imports only canonical `wasi:*` interfaces
(`wasi:filesystem`, `wasi:io`, `wasi:cli`); it does **not** import
`capa:host`. It is stock WASI, so the runtime, not the Capa host,
materializes the filesystem authority. The `--wasi` path is
experimental and opt-in.

## The compliance story in one screen

```
$ capa --manifest main.capa | jq '.summary.declassification_sites'
6

$ capa --manifest main.capa | jq '.functions[] | select(.source_name=="assess")
                                   | .provably_excluded_capabilities'
[ "Clock", "Db", "Env", "Net", "Proc", "Random", "Unsafe", ... ]
```

The fraud engine's manifest entries record no capability, with `Net`
among the excluded ones. The six disclosure points are named, with
reasons, in the manifest:

- three cardholder-data-at-rest / display bridges in `mask.capa`
  (`mask_pan`, `storable_credential`, `storable_ciphertext`);
- two in `main.process`, at the PAN-blocklist sink: the boolean
  disclosure that a transaction's PAN matched the blocklist, and the
  matched keyed fingerprint written to the fraud-alert log;
- the decision-output bridge in `main.print_decision` (an authorization
  decision is the pipeline's legitimate public output, derived from
  transaction data and risk rules, never from the PAN or CVV).

The blocklist and decision bridges live in `main.capa`, not `mask.capa`,
on purpose: Capa's flow analysis checks each function against its sinks,
so a `declassify` is only *load-bearing* in the same function as the
public sink it feeds. Placing it at the sink is what makes deleting it
break the build (see the load-bearing claim above). `mask.pan_fingerprint`
keeps its result `@secret` precisely so the disclosure decision is taken,
and audited, where the value actually leaves the program. That is the
artifact a CRA / PCI reviewer wants, produced by the compiler rather
than asserted in a PDF.

## CRA conformity pack

[`conformity/`](conformity/) is a worked EU Cyber Resilience Act
conformity pack for this program: the CycloneDX + SPDX SBOMs, the
capability manifest (with the information-flow `declassifications`), a
VEX document, and SLSA build provenance, all emitted by the compiler,
plus [`CONFORMITY.md`](conformity/CONFORMITY.md) mapping them to the
specific Annex I technical requirements they support. Regenerate it
with `./generate.sh`. It is a showcase, not a certification (see the
honesty boundary in `CONFORMITY.md`). The pack was generated **with
the compiler version it names**, currently `1.18.1`; rerunning
`./generate.sh` regenerates every artifact with its build timestamps
pinned by a fixed `SOURCE_DATE_EPOCH`. A rebuild-and-diff is a check to
run, not a guarantee. Every artefact stamps its own `capa_version`,
and a later compiler adds emitter fields that move all five files, so
the version is part of the input rather than noise to be excused.

## Releasing, and what gates it

Releases are cut from a GPG-signed `v*` tag and carry a SLSA L2
build-provenance attestation. Before anything is built or published,
`.github/workflows/release.yml` runs the compiler repository's shared
release guards, pinned by commit SHA: guard 1 refuses a tag that does
not match `[package].version`, and guard 2 extracts the tarball into an
empty directory with no siblings and runs this repository's documented
consumer flow there, with the *released* compiler the manifest floor
names. That flow imports `publisher.asc`, installs the dependencies,
compiles all eight compiling modules, checks the capability ceiling of
each, requires `leaky_example.capa` to be refused with its exact
information-flow message, and runs `capa test`.

Four checks in `tests/` keep that wiring honest and run on every push
via `.github/workflows/checks.yml`: `test_release_wiring.sh` (the
release actually gates, and every top-level `.capa` file is accounted
for), `test_wiring_mutations.sh` (that check would notice if it did
not), `test_shared_regions.sh` (the shared files have not drifted from
the compiler repository's canonical copies) and `test_guard_pins.sh`
(the guard revision pinned is the one whose bytes `.github/guard-pins.sha256`
records). `guard-selftest.yml` rehearses the whole clean room against
an existing tag without spending a version number.

## Requirement mapping (brief -> mechanism)

| Brief requirement | How Capa carries it |
|---|---|
| 4.2 SCA / MFA | `auth.sca_satisfied` (>= 2 factor classes); secrets stay `@secret` |
| 4.3 RBAC / least privilege | capability parameters; SBOM `provably_excluded_capabilities` |
| 4.4 dynamic linking, idempotency | `validate.authorization_code` / `validate.claim` |
| 4.5 SCA exemptions | `auth.evaluate_exemption` (+ recorded reason) |
| 4.6 protect sensitive data | `@secret` labels + `mask.capa` declassify bridges |
| 4.7 explainable fraud / AML | `fraud.assess` returns signals + `fraud.explain` |
| 4.8 secure logging (no secrets in clear) | information-flow check at the `Fs.write` sink |
| Audit trail integrity | `audit.capa` HMAC-SHA256 hash chain (real, via `capa_hash`) |
| SBOM / conformity evidence | `capa --manifest` (`declassifications`, per-function capability record) |
