# CRA conformity pack: capa_paymentguard

A worked **EU Cyber Resilience Act** (Regulation (EU) 2024/2847)
conformity pack for the `capa_paymentguard` showcase. It bundles the
machine-readable artifacts the Capa compiler emits for this program
and maps them to the specific Annex I technical requirements they
support.

The point of this pack: the evidence below is **generated by the
compiler from the source**, not asserted in prose. An assessor reads
the artifacts alongside the policy documents.

## Honesty boundary (read first)

This is a **language showcase**, not a certified product.

- The integrity / authentication crypto is REAL; confidentiality and
  the credential KDF are still stubs. HMAC-SHA256 (the audit hash
  chain, the PAN fingerprint, the dynamic-linking code) and the
  constant-time tag comparison come from the `capa_hash` dependency: a
  zero-capabilities Capa library whose release is GPG-signed and
  SLSA-attested and verified by `capa install`. Those are genuine
  HMAC-SHA256 values. What stays FAKE in `crypto_stub.capa` is exactly
  what `capa_hash` does not cover: the credential **KDF** (`slow_hash`,
  which belongs to Argon2id, not a bare SHA) and the at-rest **cipher**
  (`encrypt`, which belongs to AES-256-GCM under a KMS data key). A
  real product still replaces those two with vetted primitives behind a
  KMS. The pack demonstrates the data-flow discipline *around* the
  crypto; the integrity half of the crypto is now real and verifiable.
- Capa is a programming language: it addresses the **technical** slice
  of Annex I that interacts with how a product is built and described.
  The **organisational** CRA obligations (vulnerability disclosure
  policy, incident notification, conformity assessment modules, update
  distribution) are the manufacturer's regardless of language, and are
  out of scope here.
- The information-flow check has the boundaries listed in the project
  README. It reports the flows the analysis detects; an accepted program
  is not thereby proved free of secret-to-sink flows.
- The pack is generated by, and the program pins (`capa = ">=1.18.1"`), a
  compiler that carries the `1.3.0` soundness fixes. Capa `1.3.0`
  tightened the analysis so a `@secret` routed through a `match` / `if`
  value or a capturing closure, or a captured secret leaked across a
  function boundary through a higher-order callee, is now reported
  rather than silently dropped; measured here, `1.2.0`
  misses one of this program's own flows and `1.3.0` reports it. See the
  compiler advisory
  [`docs/advisories/2026-06-16-soundness.md`](https://github.com/nelsonduarte/capa-language/blob/main/docs/advisories/2026-06-16-soundness.md).
  The declared floor is higher than that boundary because no released
  binary before `1.18.1` can run this repository's own test suite; the
  measurement is in `capa.toml`. The `capa_version: 1.18.1` field stamped
  into every artifact below records the compiler these bytes came from.

## Artifacts in this pack

| File | What it is | Generated by |
|---|---|---|
| `manifest.json` | Per-function capability manifest + IFC declassifications | `capa --manifest main.capa` |
| `sbom.cyclonedx.json` | CycloneDX 1.5 SBOM with capability metadata | `capa --cyclonedx main.capa` |
| `sbom.spdx.json` | SPDX 2.3 SBOM | `capa --spdx main.capa` |
| `vex.cyclonedx.json` | VEX (exploitability statements) | `capa --vex main.capa` |
| `provenance.slsa.json` | SLSA v1 build provenance | `capa --provenance main.capa` |

The pack was generated **by the compiler version it names**. To
regenerate it: clone the repo, check out this commit, install capa
**`1.18.1`** (the floor `capa.toml` declares, and the version stamped
in `capa_version` below), run `capa install` (to vendor and verify
`capa_hash`), then run `./generate.sh` from the repo root. It writes
`manifest.json`, `sbom.cyclonedx.json`, `sbom.spdx.json`,
`vex.cyclonedx.json` and `provenance.slsa.json` with their build
timestamps pinned. The compiler's tests pin byte-identical output for
repeated runs of the same program; a rebuild-and-diff is a check to
run, not a guarantee. The compiler writes these artefacts with LF
newlines through the binary stdout buffer (no platform translation),
and `.gitattributes` pins the checked-out pack to LF, so line endings
do not differ between Linux, macOS, and Windows, or with an assessor's
`core.autocrlf` setting.

**The compiler version is part of the input, not part of the noise.**
Every artefact carries a `capa_version` field, and later releases add
fields the emitters did not have before: regenerating this pack on
`1.19.0` moves all five files. That is the emitters improving rather
than the build drifting, but it means a rebuild-and-diff is a check
against one compiler version and is written that way here. A pack
regenerated with a different release should be committed together with
the floor that names it.

The build timestamps are pinned, not stamped at run time:
`generate.sh` reads a fixed Unix epoch from the versioned
`conformity/SOURCE_DATE_EPOCH` file and exports it as `SOURCE_DATE_EPOCH`
(the reproducible-builds.org convention), so the compiler derives
`timestamp`, `created`, `annotationDate`, `startedOn`, and `finishedOn`
from that instant instead of the wall clock. The epoch is a constant in
the repo, deliberately *not* derived from the commit time (that would be
circular: the pack is generated and committed together, and an assessor
checking out the commit would observe a different HEAD time), and is
bumped by hand per release.

## Headline findings for this program

Read straight off `manifest.json`:

- **70 functions** (the program plus the verified `capa_hash`
  dependency it now pulls in), **0 crossing `Unsafe`** (no FFI /
  raw-pointer escape hatch anywhere in the program or its dependency).
- **6 declassification sites**, every sanctioned secret-to-public
  disclosure in the program, each with a stated reason:

  | Function | Reason recorded in the manifest |
  |---|---|
  | `mask_pan` | PCI DSS 3.4: display only the last four PAN digits |
  | `storable_credential` | credential stored only as a salted slow-hash, never in clear |
  | `storable_ciphertext` | PCI DSS 3.4: PAN stored only as AES ciphertext under a KMS data key |
  | `process` | PCI DSS 3.4: disclosing that a transaction's PAN matched the blocklist drives the public refusal decision |
  | `process` | PCI DSS 3.4: a matched PAN blocklist fingerprint is recorded in the fraud-alert log; it is a keyed one-way value, not the PAN |
  | `print_decision` | authorization decision is the pipeline's public output: approve/decline/review plus a rule-derived reason, no cardholder data |

  The first three (in `mask.capa`) disclose *derived forms of cardholder
  data* at rest or for display. The two in `process` are the
  PAN-blocklist sink: the `@secret` PAN fingerprint is matched, in
  constant time, against a public watchlist, and on a hit both the match
  result and the matched fingerprint are written to a fraud-alert file.
  The last (in `print_decision`) discloses the authorization *decision*,
  which carries no cardholder bytes.

  These bridges are **load-bearing**: `process` opts into `@strict_ifc`,
  so deleting either of its declassifies makes `capa --check main.capa`
  fail (a `@secret` value reaches `Fs.write`, or `Fs.write` runs under
  secret control flow). `mask.pan_fingerprint` deliberately keeps its
  result `@secret` so the disclosure decision is taken, and audited, at
  the sink where the value actually leaves the program.

- **Least privilege, checked by the compiler**: the fraud / AML engine
  (`assess`, `risk_to_decision`) declares **no capabilities**, its
  capability set is provable from its types, and the manifest lists
  `Net` (and `Fs`, `Env`, `Clock`, `Db`, `Proc`) in its
  `provably_excluded_capabilities`.

Everything else in the program is checked at compile time: a flow the
analysis detects from a card number (`@secret`) to a log line or a
network call, without passing through one of the declassify bridges
above, is a build error in `process` (`@strict_ifc`) and a warning
elsewhere.

## CRA Annex I mapping

Only the rows this program supplies concrete evidence for are listed.
See [`docs/cra.md`](https://github.com/nelsonduarte/capa-language/blob/main/docs/cra.md)
in the compiler repo for the full article-by-article treatment.

| CRA reference | Requirement (paraphrased) | Evidence in this pack |
|---|---|---|
| Annex I Part I (2)(b) | secure-by-default configuration | Every function defaults to zero capabilities; `manifest.json` shows each function's declared set is exactly what its signature carries. |
| Annex I Part I (2)(d) | protection from unauthorised access | No constructor or literal produces a built-in capability, and no global or import yields one; `manifest.json` `declared_capabilities` per function is the access-control surface. |
| Annex I Part I (2)(e) | confidentiality of processed data | IFC: card data is `@secret`; the compiler checks every path it analyses to a public sink, and the build fails (`@strict_ifc` on `process`) if it detects one that is not masked. `manifest.json` `declassifications` enumerates the 6 sanctioned disclosures with reasons. |
| Annex I Part I (2)(f) | integrity against manipulation | Each function's `transitively_reachable_capabilities` is derived by the compiler from its signature and body; an SBOM diff (`sbom.cyclonedx.json`) shows any change in that derived set, including a dependency function that gains a capability in its signature. |
| Annex I Part I (2)(g) | data minimisation | Least authority is the language default; IFC additionally checks where secret data flows and reports a flow to a sink that it detects. |
| Annex I Part I (2)(j) | limit attack surfaces / external interfaces | The declared capability set per function *is* the interface contract; `manifest.json` + the WIT spec under `capa --wasm --component` are the machine-readable surface. |
| Annex I Part I (2)(k) | reduce incident impact (exploitation mitigation) | The fraud engine declares no capability, `main` declares only `Fs` and `Stdio`, and no function in the program declares `Net`, `Proc`, `Db` or `Unsafe`. |
| Annex I Part II (1) | SBOM in a machine-readable format | `sbom.cyclonedx.json` (CycloneDX 1.5) and `sbom.spdx.json` (SPDX 2.3), listing the program's functions with their capability sets. The committed documents list the functions of the `capa_hash` dependency, not the dependency as a component with a purl. |

Out of scope for the language layer (the manufacturer's
responsibility): (2)(e) the *encryption* half, (2)(h) DoS resilience,
(2)(m) data erasure, and all of Annex I Part II beyond (1) (disclosure,
remediation timelines, update distribution).
